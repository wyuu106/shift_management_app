# シフト管理アプリ 要件定義

## 1. 目的

飲食店におけるシフト希望の収集、シフト作成、確定シフトの共有、スタッフアカウント管理をWeb上で一元化する。

従来のLINEと紙を併用した運用における、履歴確認の手間、備考を扱いにくい問題、紙への転記作業を減らすことを目的とする。

---

## 2. 対象利用者

| ロール | 主な利用目的 |
| --- | --- |
| 管理者 | シフト期間設定、希望の確認、確定シフト作成、スタッフ管理 |
| スタッフ | アカウント申請、シフト希望提出、確定シフト確認 |

ロール別の詳細要件は以下を参照する。

- [管理者要件](./admin.md)
- [スタッフ要件](./staff.md)

---

## 3. システム構成

- フロントエンド: React、Vite、JavaScript
- バックエンド: FastAPI、Python
- データベース: PostgreSQL
- ORM: SQLAlchemy
- 認証: JWT Bearer認証
- パスワード: bcryptによるハッシュ化

---

## 4. 共通機能要件

### 4.1 アカウント登録申請

1. 未ログインユーザーはID、ユーザー名、パスワード、確認用パスワードを入力する。
2. フロントエンドは未入力とパスワード不一致を検証する。
3. 申請時点では`users`へ登録せず、`user_requests`へ`pending`状態で保存する。
4. 既存ユーザーまたは申請中データとID・ユーザー名が重複する場合は受け付けない。
5. 管理者の承認後にスタッフとしてログイン可能になる。

### 4.2 ログイン・ログアウト

- ログインIDとパスワードを使用する。
- 認証成功時に有効期間6時間のJWTを発行する。
- JWTにはアカウント作成ごとの`auth_id`を含め、DBと照合する。同じIDの再登録でも以前のトークンは使用できない。
- フロントエンドはJWTとロールを`localStorage`へ保存する。
- JWTが存在しない、形式が不正、有効期限切れ、またはロールが不正な場合はログイン画面へ戻す。
- APIが401を返した場合はセッション情報を削除し、ログイン画面へ戻す。
- ログアウト前に確認ダイアログを表示する。

### 4.3 権限制御

- 認証が必要なAPIはBearerトークンから現在のユーザーを特定する。
- 管理者専用APIは`role == "admin"`を必須とする。
- フロントエンドでも管理者画面とスタッフ画面を保護し、異なるロールの画面へ直接アクセスさせない。
- 最終的な認可判断はバックエンドで行う。

### 4.4 シフト期間と営業日

- シフト期間は複数件保持し、重複しない新しい期間は既存期間を残して追加する。
- 期間は名称、開始日、終了日、営業日の一覧を持つ。
- 開始日は終了日より前でなければならない。
- 営業日は期間内の日付から選択する。
- `business_dates`に含まれない期間内の日は休業日として扱い、カレンダーに「休」と表示する。
- 管理画面で期間を変更した際、日曜日と水曜日をデフォルトの休業日とする。管理者は個別に営業日・休業日を切り替えられる。
- 期間の重複は開始日・終了日を含めて判定する。新規開始日が既存終了日以前、かつ新規終了日が既存開始日以後の場合は重複とする。
- 重複する期間がある場合は「期間が重複しているシフト期間が存在します。上書きしますか？」と確認する。
- 「はい」を選択した場合、新しい期間と重複する既存期間をすべて、その営業日とともに削除し、新しい期間と営業日を1件分登録する。
- 置き換えは既存期間全体を対象とする。新しい期間の外側にある部分も残さず、期間を分割しない。重複しない既存期間は維持する。
- 「いいえ」を選択した場合は保存せず、既存データと入力内容を維持する。
- 重複判定と保存直前の再確認はバックエンドで行う。確認対象が変わった場合は再確認を求める。
- 複数期間の削除と新規登録は1トランザクションで行い、失敗時は置き換え前の状態を維持する。
- 上書き承認時は、置き換え対象となる既存期間全体の日付範囲に属する全スタッフのシフト希望を削除する。新規期間の外側にある日付の希望も対象とする。
- 確定シフトは期間の置き換えによって削除・変更しない。新規期間の外側や新たに休業日となる日付の確定シフトも、データとして保持する。
- 保持した確定シフトの画面表示は、選択中の期間と営業日の表示ルールに従う。期間の置き換え後もデータが残ることと、画面で表示されることは区別する。
- 確定シフト登録時の対象期間内の一括更新は従来どおりとする。期間設定時の保持ルールとは別の操作として扱う。

#### ホーム画面の表示期間

- ホーム画面（ログイン後の初期シフト画面）は、現在日時から日本時間（`Asia/Tokyo`）の当日を求め、`開始日 <= 当日 <= 終了日`を満たす期間のシフトを表示する。
- 現在日時の判定基準はバックエンドとし、端末のタイムゾーンによって表示期間が変わらないようにする。
- 該当期間がない場合は「現在のシフト期間はありません」と表示する。過去・未来の期間を自動で代わりに表示しない。
- 未来の期間を新規作成しても、ホーム画面は当日を含む期間を表示する。

#### シフト確認・編集画面の期間選択

- スタッフのシフト確認画面と管理者のシフト編集画面では、シフト期間名をタップすると、他のシフト期間の選択肢を表示する。
- 初期表示では、日本時間の当日を含む期間を選択する。
- 各選択肢には、シフト期間名と開始日〜終了日を表示する。期間名が未設定の場合は「名称未設定」と表示する。
- 選択した期間の名称、開始日・終了日、営業日、確定シフトを表示する。管理者の編集画面では、シフト希望も同じ期間の情報へ切り替える。
- 管理者の編集・登録は選択中の期間を対象とし、他の期間のシフトに影響を与えない。
- 当日を含む期間がない場合も「期間を選択」から既存期間を手動で選べるようにする。期間が1件もない場合は、選択可能な期間がないことを表示する。
- 手動で選択した期間は、表示中に当日を含む期間へ自動で戻さない。
- 管理者に未保存の変更がある場合、期間切り替えにも既存の破棄確認を適用する。キャンセルした場合は選択中の期間と編集内容を維持する。

#### シフト希望提出画面の期間選択

- 初期表示は、登録済み期間のうち終了日が最も遅い期間とする。「最新」は作成日時や更新日時ではなく、期間に含まれる最も先の日付で判定する。
- シフト期間名をタップすると、シフト確認画面と同じ形式で期間名と開始日〜終了日を表示した選択肢を開く。
- 他の期間を選択すると、その期間の営業日とログイン中スタッフの登録済み希望を取得して表示する。提出も選択中の期間だけを対象とする。
- 未保存の変更がある場合は期間切り替えにも破棄確認を適用し、キャンセルした場合は選択中の期間と編集内容を維持する。
- 期間が1件もない場合は、希望提出できる期間がないことを表示する。

#### 日付の再判定

- 画面を開いた時と再読み込み時に初期表示期間を判定する。手動選択中の期間は日付変更で自動的に切り替えない。

### 4.5 カレンダー表示

- 期間が複数月にまたがる場合は月ごとに表示する。
- 日曜日と土曜日は曜日を判別できる色で表示する。
- 営業日に確定シフトがない場合は「未定」と表示する。
- 確定シフトがある場合はスタッフ名を表示する。
- 備考がある場合はスタッフ名の下へ`（備考）`形式で表示する。
- スマートフォンの7列表示でも内容を判別できる文字サイズ、余白、折り返し・省略を用いる。

### 4.6 通知と未保存データ

- シフト期間登録、確定シフト登録、シフト希望提出の成功時は中央モーダルでAPIの成功メッセージを表示する。
- 成功モーダルを閉じるまでは背後の画面を操作できない。
- シフト編集または希望編集に未保存の変更がある状態で画面遷移する場合、以下を表示する。

```text
画面を切り替えますか？
（編集中の内容は破棄されます）
```

- ページ更新やタブを閉じる操作にもブラウザ標準の離脱警告を表示する。
- 保存成功後は未保存状態を解除する。

## 5. API一覧

シフト関連の取得・一括登録APIは、クエリパラメータ`period_id`で対象期間を指定する。未指定時は、希望関連の本人取得・登録では終了日が最も遅い期間、それ以外では日本時間の当日を含む期間を使用する。

- `GET /period`の`shift_version`が確定シフトの取得時バージョンとなる。希望の本人取得APIは`version`を返す。
- `PUT /shift`と`PUT /shift/request`はクエリ`expected_version`（0以上）が必須。保存直前に照合し、不一致は409で変更せず返す。成功時は新しい`version`を返す。
- バージョンは確定シフトが期間単位、希望が本人・期間単位。削除・挿入と同じトランザクション内で更新し、失敗時はバージョンもロールバックする。
- 409時は画面の編集内容を維持し、ユーザーが確認してから最新データを再読み込みする。保存中は編集操作を無効化する。

- `GET /periods`: 全期間を終了日の降順で返す。各要素は`id`、`name`、`start`、`end`、`business_dates`を持つ。
- `GET /period`: `period_id`を指定した期間を返す。未指定時は当日を含む期間、`latest=true`の場合は終了日が最も遅い期間を返す。`period_id`を優先し、対象なしは404とする。
- `PUT /period`: `name`、`start`、`end`、`business_dates`を受け取り新規登録する。重複時は409で`detail.message`と`detail.periods`（重複期間一覧）を返す。
- 上書き承認後は`overwrite_period_ids`に確認対象の全IDを追加して再送する。サーバーが再計算した対象IDと一致しない場合は409で再確認を求める。
- 期間設定・希望登録・確定シフト登録は削除と挿入を同一トランザクションで行い、例外時にロールバックする。PostgreSQLのトランザクション単位のアドバイザリロックで、これらの更新操作を直列化する。

| Method | Path | 認証・権限 | 用途 |
| --- | --- | --- | --- |
| POST | `/init` | なし | 初回管理者作成 |
| POST | `/register/request` | なし | ユーザー登録申請 |
| POST | `/login` | なし | JWT発行 |
| GET | `/requests` | 管理者 | pendingの登録申請一覧 |
| POST | `/approve/request/{request_id}` | 管理者 | 登録申請の承認 |
| PUT | `/reject/request/{request_id}` | 管理者 | 登録申請の却下 |
| GET | `/users` | 管理者 | ユーザー一覧 |
| DELETE | `/user/{user_id}` | 管理者 | スタッフ削除 |
| GET | `/periods` | ログイン済み | 期間一覧・営業日取得 |
| GET | `/period` | ログイン済み | 現在のシフト期間・営業日取得 |
| PUT | `/period` | 管理者 | シフト期間・営業日登録 |
| GET | `/user/shift/requests` | ログイン済み | 自分の希望取得 |
| PUT | `/shift/request` | ログイン済み | 自分の希望一括登録 |
| GET | `/shift/requests` | 管理者 | 全スタッフの希望取得 |
| GET | `/shifts` | ログイン済み | 全体の確定シフト取得 |
| PUT | `/shift` | 管理者 | 確定シフト一括登録 |
| GET | `/user/shifts` | ログイン済み | 自分の確定シフト取得 |

## 6. データ要件

| テーブル | 用途 | 主な項目 |
| --- | --- | --- |
| `users` | ログイン可能なユーザー | 文字列ID、名前、ハッシュ化パスワード、ロール |
| `user_requests` | アカウント登録申請 | 申請ID、希望ユーザーID、名前、ハッシュ化パスワード、状態 |
| `shift_periods` | 複数のシフト期間 | ID、名称、開始日、終了日 |
| `business_dates` | 期間内の営業日 | ID、営業日、期間ID |
| `shift_requests` | スタッフの希望 | ID、希望日、備考、ユーザーID |
| `shifts` | 確定シフト | ID、出勤日、備考、ユーザーID |

- `users.id`、`shift_requests.user_id`、`shifts.user_id`は文字列型で統一する。
- スタッフ削除時は、そのスタッフの希望と確定シフトを外部キーの`ON DELETE CASCADE`で削除する。
- 期間と営業日の親子関係は、期間削除時に営業日も削除する。

## 7. 非機能要件

### 7.1 UI・操作性

- スマートフォンでの利用を主対象とする。
- 主要画面は固定下部ナビゲーションから移動できる。
- タップ対象は小さくなりすぎないようにする。
- 読み込み中、データなし、エラーを画面上で区別して表示する。

### 7.2 セキュリティ

- パスワードはbcryptでハッシュ化して保存する。
- JWT署名鍵、DB接続文字列、初期管理者情報は環境変数で管理する。
- CORS許可元は`ALLOW_ORIGINS`で設定する。
- 管理者専用操作はバックエンドでロールを検証する。

### 7.3 保守性

- フロントエンドはページ、共通コンポーネント、ユーティリティ、フックに責務を分離する。
- バックエンドはrouter、CRUD、schema、modelに責務を分離する。
- APIの入出力型とDBカラム型を一致させる。

## 9. 現在の対象外

現行実装に存在しない以下の機能は、本要件には含めない。

- 複数店舗管理
- シフト確認・編集画面とは独立した履歴専用画面（既存画面での過去・未来の期間選択は対象に含む）
- 勤務開始・終了時刻による詳細な勤務時間管理
- メール通知、プッシュ通知、LINE連携
- パスワード再発行
- 監査ログ、CSV出力、給与計算
