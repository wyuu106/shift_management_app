# シフト管理アプリ 要件定義

## 1. 目的

飲食店におけるシフト希望の収集、シフト作成、確定シフトの共有、スタッフアカウント管理をWeb上で一元化する。

従来のLINEと紙を併用した運用における、履歴確認の手間、備考を扱いにくい問題、紙への転記作業を減らすことを目的とする。

---

## 2. 対象利用者

| ロール | 主な利用目的 |
| --- | --- |
| 管理者 | シフト期間設定、希望の確認、確定シフト作成、スタッフ管理 |
| スタッフ | アカウント申請、シフト希望提出、確定シフト確認 |

## 4. システム構成

- フロントエンド: React、Vite、JavaScript
- バックエンド: FastAPI、Python
- データベース: PostgreSQL
- ORM: SQLAlchemy
- 認証: JWT Bearer認証

## 5. 共通機能要件

### 5.1 アカウント登録申請

1. 未ログインユーザーはID、ユーザー名、パスワード、確認用パスワードを入力する。
2. フロントエンドは未入力とパスワード不一致を検証する。
3. 申請時点では`users`へ登録せず、`user_requests`へ`pending`状態で保存する。
4. 既存ユーザーまたは申請中データとID・ユーザー名が重複する場合は受け付けない。
5. 管理者の承認後にスタッフとしてログイン可能になる。

IDは半角英数字・`-`・`_`の1〜64文字とする。画面とAPIの両方で検証する。

### 5.2 ログイン・ログアウト

ログイン

- ログインIDとパスワードを使用する。
- 認証成功時に有効期間6時間のJWTを発行する。
- JWTにはアカウント作成ごとの`auth_id`を含め、DBと照合する。同じIDの再登録でも以前のトークンは使用できない。
- フロントエンドはJWTとロールを`localStorage`へ保存する。

セッションの失効

- JWTが存在しない、形式が不正、有効期限切れ、またはロールが不正な場合はログイン画面へ戻す。
- APIが401を返した場合はセッション情報を削除し、ログイン画面へ戻す。

ログアウト

- 実行前に「ログアウトしますか？」と確認する。
- 承認された場合はJWTとロールを削除し、ログイン画面へ移動する。

### 5.3 権限制御

- 認証が必要なAPIはBearerトークンから現在のユーザーを特定する。
- 管理者専用APIは`role == "admin"`を必須とする。
- フロントエンドでも管理者画面とスタッフ画面を保護し、異なるロールの画面へ直接アクセスさせない。
- 最終的な認可判断はバックエンドで行う。

### 5.4 シフト期間と営業日

詳細は[シフト期間のルール](./period.md)に書く。要点は次のとおり。

- シフト期間は複数件保持する。重複しない新しい期間は、既存期間を残して追加する。
- 重複する場合は確認し、承認されたら重複する既存期間全体を新しい1件へ置き換える。対象期間のシフト希望は削除し、確定シフトは保持する。
- 期間内で`business_dates`に含まれない日は休業日として扱う。
- シフト確認・編集は日本時間の当日を含む期間、希望提出は終了日が最も遅い期間を初期表示する。どの画面でも他の期間を選択できる。

### 5.5 カレンダー表示・通知・未保存データ

画面の表示と操作は[UI要件](./ui.md)に書く。

- カレンダーの表示: UI要件 3章
- 登録成功時のポップアップ: UI要件 2.4
- 未保存の変更がある状態での離脱警告: UI要件 2.6

## 6. 非機能要件

### 6.1 UI・操作性

- スマートフォンでの利用を主対象とする。
- 詳細は[UI要件 2章](./ui.md)を参照。

### 6.2 セキュリティ

- パスワードはbcryptでハッシュ化して保存する。
- JWT署名鍵、DB接続文字列は環境変数で管理する。
- 初期管理者はAPIでは作成しない。サーバー上で`backend/`から`python -m scripts.create_admin --id <ID> --name <名前>`を実行して作成する。パスワードは対話入力し、環境変数やコマンド引数に置かない。管理者が既に存在する場合は作成しない。
- CORS許可元は`ALLOW_ORIGINS`で設定する。
- 管理者専用操作はバックエンドでロールを検証する。
- 本番環境のネットワークと機密情報の扱いは[インフラ設計 3章](../infrastructure/architecture.md)を参照。

### 6.3 保守性

- フロントエンドはページ、共通コンポーネント、ユーティリティ、フックに責務を分離する。
- バックエンドはrouter、CRUD、schema、modelに責務を分離する。
- APIの入出力型とDBカラム型を一致させる。
- 各ディレクトリの責務は[ディレクトリ構成](../architecture/directory-structure.md)を参照。

## 7. 環境変数

### Backend

| 変数 | 用途 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL接続文字列 |
| `SECRET_KEY` | JWT署名鍵 |
| `ALLOW_ORIGINS` | CORS許可元。複数の場合はカンマ区切り |
| `ENABLE_API_DOCS` | `true`のときだけ`/docs`・`/redoc`・`/openapi.json`を公開する。ローカル開発用で、本番では設定しない |

### Frontend

| 変数 | 用途 |
| --- | --- |
| `VITE_API_URL` | バックエンドAPIのベースURL。未指定時は`http://localhost:8000` |

## 8. 現在の対象外

現行実装に存在しない以下の機能は、本要件には含めない。

- 複数店舗管理
- シフト確認・編集画面とは独立した履歴専用画面（既存画面での過去・未来の期間選択は対象に含む）
- 勤務開始・終了時刻による詳細な勤務時間管理
- メール通知、プッシュ通知、LINE連携
- パスワード再発行
- 監査ログ、CSV出力、給与計算
