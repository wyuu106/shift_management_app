# デプロイの流れ

2026年11月の初回デプロイで行った操作をまとめる。コマンドの詳細は`infra/README.md`、構成と理由は`architecture.md`を参照。

## 全体像

| 段階 | 主な操作 | 場所 |
| --- | --- | --- |
| 1. 事前準備 | AWSにログインし、プラン・料金・通知先を確認する | 手元のPC |
| 2. AWSリソース作成 | CDKでサーバー・固定IP・バケット・アラームを作る | 手元のPC |
| 3. サーバー初期設定 | SSHで入り、ソフトの導入とDBの作成を行う | サーバー |
| 4. アプリ起動 | アプリを起動し、初期管理者を作る | サーバー |
| 5. バックアップ | バケットへの自動バックアップを有効にする | 手元のPC＋サーバー |
| 6. 復旧の練習 | バックアップからDBを戻せることを確かめる | サーバー |
| 7. ドメインとHTTPS | ドメインをサーバーに向け、証明書を取る | Vercel＋サーバー |
| 8. Vercelと接続 | 画面の接続先を新しいAPIに切り替える | サーバー＋Vercel |

## 1. 事前準備

- `aws login`でAWSにログインした。
- アカウントが無料プラン（クレジット制）で、Lightsailを使えることを確認した。
- `micro_3_2`（1GB、月7ドル、ディスク40GB）と`small_1_0`（バケット、月1ドル）がシドニーにあることを確認した。
- アラームの通知先メールをCLIで登録し、届いた確認メールのリンクを開いて有効にした。通知先はCloudFormationで作れないため、デプロイ前に登録する。
- デプロイするコードを`dev`から`main`へPRでマージした。サーバーは`main`をcloneするため。

## 2. AWSリソース作成

- `cdk diff`で、作られるのが追加5件だけで、置き換えや削除がないことを確認した。
- SSHは自宅のIPとLightsailのブラウザ版SSHからだけ許可するよう、自宅のIPを指定した。
- 通常のターミナルで`safe-deploy.sh`を実行し、表示された変更内容を確認して`yes`を入力した。
  - Claude Codeの`!`から実行すると`yes`を入力できず、確認の手前で終了した（何も作られない）。
- 作成後、サーバーが起動中で固定IPが付いていること、バケットが非公開であること、アラームの通知先がメールであることを確認した。

## 3. サーバー初期設定

- Lightsailのデフォルトキーペアの秘密鍵をダウンロードし、SSHで接続した。
- 管理用のリポジトリを`~/shift-management-app`にcloneした。
  - 保存先を省いたため`shift_management_app`というフォルダになり、`mv`で名前を直した。
- `setup.sh`を実行した。swap、Nginx、PostgreSQL、ファイアウォール、アプリ専用ユーザー`shiftapp`、systemdの設定がそろう。
  - 外から`/health`を開くと502になり、Nginxが動いていてアプリがまだないことを確認した。
  - `swapon --show`で2GBのswapを確認した。
- `shiftapp`としてアプリ用のリポジトリを`/opt/shift-management/app`にcloneした。管理用とアプリ用を分け、アプリが乗っ取られてもroot用のスクリプトを書き換えられないようにしている。
- `setup-db.sh`でDB、DBユーザー、`backend.env`（DB接続先と`SECRET_KEY`）を作った。パスワードは自動生成され、画面には出ない。

## 4. アプリ起動

- `deploy.sh`を実行した。事前リハーサル、バックアップ、依存導入、マイグレーション、起動、起動確認まで自動で行う。
- 外から`/health`が`{"status":"ok"}`を返し、APIの説明ページ（`/docs`）が非公開であることを確認した。
- `create_admin`で初期管理者を作った。パスワードは対話で入力する。
- HTTPSにするまで、ブラウザからはログインしなかった（パスワードが暗号化されずに流れるため）。

## 5. バックアップ

- 手元のPCでバケット専用のアクセスキーを発行した。シークレットは1回しか表示されないため、自分のターミナルで実行し、会話には貼らなかった。
- サーバーに`backup.env`（root以外は読めない）を作り、キーとバケット名を書いた。
- 手動でバックアップを1回実行し、サーバー内とバケットの両方に保存されたことを確認した。
- 毎日03:00（日本時間）の自動実行を有効にした。保存期間はサーバー内が約7日、バケットが30日。

## 6. 復旧の練習

- 管理者の名前をわざと書き換え、バックアップ後に壊れた状態を作った。
- サーバーが壊れた場合を想定し、バケット上のバックアップから`restore-db.sh`で復旧した。確認ではDB名を入力する。
- 名前が元に戻り、アプリが自動で起動して`/health`がOKを返すことを確認した。
- 途中でバケットの一覧表示が`AccessDenied`になった。READMEのコマンドに`set -a`がなく、キーが`aws`に渡っていなかったため。READMEを修正した（スクリプトは影響なし）。

## 7. ドメインとHTTPS

- `yumeri-shift.com`をVercelで購入した。DNSもVercelで管理している。
- VercelのDNS設定で、`api`のAレコードを固定IPに向けた。
- 複数のDNSサーバーで反映を確認し、`http://api.yumeri-shift.com/health`が応答することを確かめた。
- サーバーでNginxの`server_name`を`api.yumeri-shift.com`に書き換え、`certbot`でLet's Encryptの証明書を取った。証明書は自動更新される。
- HTTPSで応答すること、HTTPがHTTPSへ転送されることを確認した。

## 8. Vercelと接続

- Vercelで画面のURLを`www.yumeri-shift.com`にした。`yumeri-shift.com`は`www`へ転送される。
- サーバーの`backend.env`の`ALLOW_ORIGINS`に、`https://www.yumeri-shift.com`と、まだ開ける`*.vercel.app`のURLを書き、アプリを再起動した。
  - 許可したURLからの呼び出しだけが通り、それ以外は拒否されることを確認した。
- Vercelの環境変数`VITE_API_URL`を`https://api.yumeri-shift.com`にして再デプロイした。Viteはビルド時に値を埋め込むため、再デプロイが必要。
- 公開中の画面が、Railwayではなく新しいAPIを向いていることを確認した。

## つまずいた点

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `safe-deploy.sh`が確認の手前で終わる | Claude Codeの`!`では`yes`を入力できない | 通常のターミナルで実行する |
| SSHがタイムアウトする | 自宅のIPが変わり、許可したIPと合わなくなった | IPが戻るのを待つか、ブラウザ版SSHを使う。恒久的には`safe-deploy.sh`を新しいIPで再実行する |
| `setup.sh: No such file or directory` | cloneのフォルダ名が`shift_management_app`になった | `mv`で`shift-management-app`に直す |
| バケットの一覧表示が`AccessDenied` | `source`だけでは`backup.env`の値が`aws`に渡らない | `set -a`を付ける（README修正済み） |
| CORSで400になる | `ALLOW_ORIGINS`が仮の値のままだった | 画面のURLを書き、アプリを再起動する |
